## Задание средней сложности: 3. Рефакторинг «плохого» кода.
### Промпт 1
**Инструмент:** OpenCode \
**Промпт:** я добавил в crud.py намеренно плохую функцию p(). отрефактори ее с объяснением каждого изменения
**Результат:** Функция отрефакторена. Вот объяснение каждого изменения в функции p():

Что было изменено и почему
1. Имя функции p → process_monthly_accruals
Имя p ничего не говорит о назначении. Новое имя описывает бизнес-логику: обработка ежемесячных начислений.

2. Неиспользуемые параметры x2-x5 удалены, x1 переименован в period_prefix
Пять безымянных параметров, из которых 4 не использовались. Теперь один параметр с понятным именем.

3. Магические числа вынесены в константы
1.2, 150, 0.05, 5000 и т.д. разбросаны по коду. Теперь: PENALTY_RATES, DISCOUNT_AMOUNTS, COMMISSION_RATES, CRITICAL_THRESHOLD.

4. Дублирование кода устранено через helpers
Логика пеней, комиссий, скидок повторялась для каждого "типа" (type 1/2/3). Вынесена в _calculate_overdue_penalty и словари-константы.

5. Несуществующие поля (type, amount, status, penalty, period) заменены на реальные
Модель Bill не содержит этих полей. Использованы: account_number (префикс для определения типа), accruals/payments/debt. Добавлена _determine_account_type.

6. Типизация добавлена
p не имела type hints. Теперь: process_monthly_accruals(db: Session, period_prefix: str) -> MonthlyProcessingResult.

7. Переменные a, b, c, d, e переименованы
a → all_bills, b → processed_bills, c → total_debt, d → period_bills, e → total_commission.

8. Два db.commit() → один в логической группе
Было два коммита в разнобой. Теперь: первый после обработки периода, второй после маркировки критических.

9. Возврат неструктурированного кортежа (b, c, e) → MonthlyProcessingResult
Непонятно, что за числа возвращались. Теперь датакласс с именованными полями.

10. Неиспользуемая копия списка устранена
Цикл for i in a: b.append(i) просто копировал список. Убран.
